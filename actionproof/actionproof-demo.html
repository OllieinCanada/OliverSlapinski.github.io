    03 / REAL HTTP + SQLITE

    Beyond simulation: disconnect, restart, retry.

    A loopback HTTP server commits synthetic approvals to SQLite. The harness disconnects responses, terminates the server after commit, restarts it against the same database, and sends 20 concurrent requests. It evaluates the database directly rather than trusting the HTTP response.

    04 / THE ENGINEERING

    Separate intent,
    effect, and evidence.

    Each run has a durable server effect log and a separate stream of observations available to the policy. The evaluator checks the effect log after the policy stops. It never takes “success” at face value.

    What does “unsafe” mean?

    A duplicate side effect, an effect on the wrong target, or a reported success without exactly one correct effect. A single run can violate more than one invariant.

    What makes a retry safe here?

    The simulated server atomically binds an operation key to a durable receipt. Reusing that key inside its documented retention window returns the original receipt. The real adapter uses a SQLite transaction to bind the key, payload, target check, and effect. Its keys do not expire. These are server capabilities; a browser automation client cannot invent them.

    What doesn’t this prove?

    This is not a benchmark of any LLM or production agent. The simulation and real HTTP experiments are chosen counterexamples, not representative failure rates. The adapter tests one local SQLite database, process restarts, and concurrent clients. It does not test replica failover, machine power loss, real browser automation, or external financial systems.

    How can I reproduce it?

    Run node cli.mjs --json for simulation results. Run python3 -m adapter.benchmark --output dist/adapter-evidence.json for the real experiments, then node scripts/bundle.mjs to embed their measured report. Neither command calls a model or external system.
