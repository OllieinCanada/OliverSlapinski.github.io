# ActionProof

**Did the action happen—or did the agent just say “done”?**

**[Open the live demo](https://actionproof-ollie.onrender.com)** · [Case study](docs/case-study.md) · [Protocol design](docs/real-adapter.md)

ActionProof is a dependency-free fault-injection lab for consequential agent actions. It separates dispatch acknowledgements, UI observations, durable side effects, and the evidence used to claim success. A browser demo and a Node CLI share a deterministic simulation engine; a real HTTP + SQLite adapter tests disconnects, process restart, and concurrent clients against durable records.

This prototype evaluates explicit protocol policies and server mechanisms, not language models. All data is synthetic. The simulation and real HTTP counterexamples are not a representative sample or production failure-rate estimate.

## Try it in 30 seconds

Open **[actionproof-demo.html](actionproof-demo.html)** in a modern browser. It is a self-contained offline demo: no installation, server, credentials, or model API required. GitHub's file preview does not execute it; download the file first.

For the CLI, use Node 24 (developed with 24.19.0):

```sh
node cli.mjs
node cli.mjs --scenario lost-ack --strategy retry
node cli.mjs --scenario lost-ack --strategy guarded --json
```

The first trace shows an approval committed twice after a lost acknowledgement. The second reconciles the first commit and stops after one dispatch. Change to `read-outage` to see the original operation key deduplicate a retry when the status lookup is unavailable.

## The question

After a timeout, an agent cannot infer whether the application committed its action. Retrying without an idempotency guarantee can duplicate the effect. A “Success” label may predate the action. And detecting a target change after dispatch is too late to prevent a wrong-target effect.

ActionProof makes these failures inspectable rather than hiding them in a single success score.

## What is implemented

- A discrete-event simulator with separate server, browser, fault, and policy events.
- Eight inspectable scenarios: clean execution, lost acknowledgement, delayed UI, stale confirmation, target drift, pre-commit request loss, status-read outage, and expired idempotency guarantee.
- Three policies: blind retry, causal UI observation, and target guarding plus idempotent reconciliation.
- An evaluator that checks the durable effect log independently of the policy's claimed outcome.
- A browser trace viewer with step/play controls, adjustable observation budget, a comparison matrix, and JSON exports.
- A real loopback HTTP server and SQLite WAL receipt store with atomic target checks and command/key binding.
- Real disconnect-after-commit, process-exit/restart, and 20-client concurrency experiments, including unsafe controls.
- A deterministic CLI, Node regression/contract tests, Python unit/integration tests, and an offline demo builder.

## Run the real adapter

Python 3.12+ is sufficient; no third-party packages are required for the adapter.

```sh
python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 -m adapter.benchmark --output dist/adapter-evidence.json
node scripts/bundle.mjs
```

The browser then embeds a report generated by actual loopback HTTP requests, SQLite writes, and a process restart. Every measured case is checked with direct SQL. The report records its runtime and source commit when available; a failed experiment does not produce a success report. Two controls deliberately demonstrate duplicate or wrong-target effects. See [real adapter design and assumptions](docs/real-adapter.md) and the [case study](docs/case-study.md).

## Results on the included corpus

Run `node cli.mjs --budget 3` to reproduce these **simulation** counts:

| Policy | Correctly completed | Unsafe | Unknown | Rejected |
|---|---:|---:|---:|---:|
| Blind retry | 3 / 8 | 5 / 8 | 0 / 8 | 0 / 8 |
| Causal observation | 1 / 8 | 1 / 8 | 7 / 8 | 0 / 8 |
| Guard + reconcile | 5 / 8 | 0 / 8 | 1 / 8 | 2 / 8 |

These columns are not mutually exclusive: an unknown outcome can still have caused an unsafe effect. “Completed” requires both a success claim and exactly one effect on the intended target. “Rejected” is an explicitly rejected request, not task completion. Observation budgets use logical ticks, not measured network latency.

The guarded policy still leaves an outcome **unknown** after its idempotency guarantee expires. It does not get credit for completing a task by refusing a risky retry.

## Design and assumptions

See [the protocol model](docs/protocol.md) for event order, receipt semantics, and trust boundaries.

For an interview or project walkthrough, use the [90-second demo guide](docs/demo-walkthrough.md).

The simulator deliberately provides stronger server capabilities to the guarded policy: an atomic target precondition, a durable operation receipt, and bounded idempotency-key retention. This is a demonstration of what those capabilities enable, not a claim that a browser agent alone can provide exactly-once execution. UI observation assumes an operation identifier is exposed by the application.

The evaluator observes the server's effect log after a run. Policies do not receive that log and can use only explicit dispatch responses, snapshots, and reconciliation responses.

## Develop

There are **zero package dependencies** and no install step.

```sh
node --test --test-isolation=none
node --experimental-vm-modules scripts/check.mjs
node scripts/bundle.mjs
node scripts/serve.mjs
```

The optional server prints `http://127.0.0.1:4173`. The standalone HTML is easier to share and works without it. The syntax checker uses Node's built-in VM module parser, which still emits an experimental-feature warning. Tests run in one process so they work in restricted environments; they do not disable assertions or skip scenarios.

The simulated guarded-policy invariant is checked for all eight scenarios at every supported observation budget from 1 through 50. Separate SQLite and HTTP tests cover durable key binding, conflicting payloads, target-guard rollback, concurrent clients, disconnects, process restart, and malformed requests. See [validation](docs/validation.md) for actual execution results and environment limits.

## Why this exists

This project develops a reliability problem I worked on in [agent-orchestrator's browser postconditions](https://github.com/OrchestratorInc/agent-orchestrator/pull/4783): input dispatch and observable application success are different facts. ActionProof is an independent teaching and evaluation prototype, not part of that upstream implementation.

## Limits and next experiment

There are no real browser automation adapters, replicated servers, financial transactions, external agents, or model calls in this version. The corpus is public and small, so it cannot establish general agent performance. Events in the simulator include server ground truth for explanation; this is not the policy's observation stream. The real adapter uses one local SQLite database and never expires its keys.

The next useful experiments would cover additional crash cut points, multi-process writers, retention and eviction contracts, and cancellation. The current process-exit checks do not simulate storage power loss or establish distributed exactly-once execution.
